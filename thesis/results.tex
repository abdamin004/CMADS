\chapter{Results}
\label{chap:results}

% ─────────────────────────────────────────────────────────────────────────────
\section{Overview}
\label{sec:results_overview}
% ─────────────────────────────────────────────────────────────────────────────

This chapter reports the results of the multi-agent clinical decision support
system described in Chapter~\ref{chap:methodology}. The system was run on the
completed subset of the Synthea-derived evaluation cohort and judged with the
LLM-as-Judge method from Section~\ref{sec:evaluation}. The chapter answers
three main questions. First, how often does the system find the target disease
in its differential diagnosis? Second, what changes when multi-level memory is
enabled? Third, how do the results compare with the literature reviewed in
Chapter~\ref{chap:background}? The chapter also reports per-agent reliability,
latency, example patient runs, dashboard review, and limitations.

% ─────────────────────────────────────────────────────────────────────────────
\section{Experimental Setup}
\label{sec:results_setup}
% ─────────────────────────────────────────────────────────────────────────────

\paragraph{Cohort.} The Gold layer contains 270 candidate patients after
deterministic filtering and the LLM-based detectability verifier
(Section~\ref{sec:llm_verifier}). The results reported here use the 160
patients that completed the full seven-agent pipeline. These patients cover
the target disease groups used in the thesis: ischemic heart disease (IHD),
chronic congestive heart failure (CHF), essential hypertension, type-2
diabetes mellitus (T2DM), end-stage renal disease and chronic kidney disease
stages 1--3 (reported together as ESRD~/~CKD), and metabolic syndrome~X. The
CKD substages are separate SNOMED labels in the data, but they share one NICE
management pathway, so they are grouped for reporting. The agents do not see
the ground-truth condition during inference; only the evaluator receives it.

\paragraph{Models and infrastructure.}
The main reasoning model is GPT-OSS-120B served through Groq. The evaluator is
Qwen3-32B, also served through Groq. Both are accessed through the provider
adapter described in Section~\ref{sec:env}. Qdrant is used for NICE guideline
retrieval and case-based memory. The data pipeline, prompt rendering, agent
orchestration, and evaluation scripts run on an Apple Silicon workstation. The
Streamlit dashboard and React doctor console are served locally.

\paragraph{Pipeline configuration.}
All runs use the default values in \texttt{src/config.py}: maximum diagnostic
rounds of 3, confidence threshold of 75, per-agent timeout of 300 seconds, and
capped exponential retry. Prompt templates are loaded from
\texttt{prompts/\{agent\_id\}.yaml}. No prompt or threshold was tuned after
seeing the reported results. Run files are saved under
\texttt{data/gold/mas\_results\_*/}, with one folder per patient UUID. Each
folder contains one JSON file per agent and an \texttt{execution\_trace.json}
timeline. The metrics below are computed from those files.

% ─────────────────────────────────────────────────────────────────────────────
\section{Evaluation Metrics}
\label{sec:results_metrics}
% ─────────────────────────────────────────────────────────────────────────────

The evaluator produces five main values for each patient. \textbf{Match type}
is DIRECT, INDIRECT, or MISS. DIRECT means the target disease appears in the
differential as a clear match. INDIRECT means the system found a clinically
related disease. MISS means it did not find the target disease or an acceptable
proxy. \textbf{Rank-when-found} records where the matched disease appears when
the judge returns DIRECT or INDIRECT. \emph{Rank-1-when-found} is the share of
found cases where the match is ranked first. \textbf{Per-agent status} records
success, partial, error, or skipped in \texttt{execution\_trace.json}.
\emph{Partial} means the output was recovered after a validation issue.
\emph{Error} means the agent failed and downstream agents carried a
\texttt{null} value. \emph{Skipped} means the agent was intentionally bypassed,
as with Treatment Planning when the match is not DIRECT. \textbf{Per-agent
latency} is the wall-clock time for each agent call. The memory study also
uses a leakage control: cases used to populate case-based memory should not be
the same cases used to evaluate with-memory performance.

Diagnostic Reasoning is the slowest stage, with a mean runtime of about

also shows the value of graceful degradation: when a Stage~1 output was only
partial, the later agents still ran and produced a final diagnosis. No patient
run failed completely because of an upstream agent error.

\section{Adaptive Reasoning and Reviewer/Refiner Effects}
\label{sec:results_adaptive}
% ─────────────────────────────────────────────────────────────────────────────

Two design choices can be checked from the run files: the adaptive diagnostic
loop and the non-destructive Reviewer-Refiner pattern from
Section~\ref{sec:agent_refiner}.

The Reviewer-Refiner pattern had a visible effect. In about three out of five
runs, the Diagnostic Refiner changed the primary diagnosis originally produced
by the Diagnostic Reasoning agent. This happened because the Refiner does not
delete the original diagnostic output; it can change the final primary while
keeping the earlier output available for audit. The Reviewer also often flagged
anchoring on one strong lab value, such as creatinine pushing the agent toward
ESRD when the full patient history supported another primary condition. The
Refiner then re-weighted the differential using that critique.

The Diagnostic Reasoning agent also used its bounded self-critique loop. The
loop stops when confidence reaches 75 or after three rounds. In the memory runs
where \texttt{session\_memory.json} is available, most cases stopped after one
round, about a third stopped after two rounds, and the rest used all three
rounds. This saves time on easier cases and leaves more reasoning budget for
harder ones.

\section{Multi-Level Memory A/B Study}
\label{sec:results_memory_ab}
% ─────────────────────────────────────────────────────────────────────────────

This section compares the four-tier shared memory design from
Section~\ref{sec:shared_memory} with the same pipeline when memory is disabled.
The comparison is reported across all processed patients for each setting, so
it is not based on one selected batch.

In the \emph{single-level} setting, only the per-run \texttt{PipelineState} is
active. The system does not write the episodic event timeline, does not use the
semantic disease store, and does not query or populate the case-based Qdrant
store. In the \emph{multi-level} setting, all four tiers are enabled. Both
settings use the same prompts, diagnostic model, judge model, retry policy, and
timeouts. Only memory changes.

Table~\ref{tab:memory_aggregate} shows the aggregate result. The single-level
setting has the higher DIRECT rate. The multi-level setting has the higher
found rate and the lower MISS rate. In plain terms, memory helps the system
include more related diagnoses, but it does not improve how often the exact
target is placed as the primary diagnosis.

\begin{table}[!htbp]
\centering
\caption{Aggregate memory comparison across all evaluated patients.
Both configurations use identical agent prompts, the same diagnostic
and judge models, and the same retry and timeout settings; only the
shared-memory subsystem differs.}
\label{tab:memory_aggregate}
\footnotesize
\begin{adjustbox}{max width=\textwidth}
\begin{tabular}{@{}lrrrrr@{}}
\toprule
\textbf{Configuration}            & \textbf{DIRECT} & \textbf{INDIRECT} & \textbf{MISS} & \textbf{Found} & \textbf{Rank-1 in found} \\
\midrule
Single-level (memory disabled)    & 69\%            & 20\%              & 12\%          & 88\%           & 64\%                     \\
Multi-level memory                & 49\%            & 46\%              &  5\%          & 95\%           & 65\%                     \\
\bottomrule
\end{tabular}
\end{adjustbox}
\end{table}

The likely explanation is that case-based memory broadens the differential. It
surfaces related disease-family priors more often than the memory-disabled
setting. This can help when a doctor reads the full differential, but it can
hurt if the system is judged only by the primary diagnosis. The Reviewer-Refiner
step does not fully remove this effect because the reviewer also sees outputs
that were influenced by memory.

The leakage control is important. If the memory store contains the same patients
used for evaluation, then retrieval can return near-duplicate prior runs from
the test set. That would inflate the with-memory result. In this thesis, the
memory-population and evaluation portions are separated for the reported
comparison. This makes the memory result more honest, even though the memory
study is still limited in size.

\section{Comparison with the Literature}
\label{sec:results_literature}
% ─────────────────────────────────────────────────────────────────────────────

The papers reviewed in Chapter~\ref{chap:background} provide context for these
results, but direct accuracy comparison is difficult. The studies use different
datasets, tasks, and metrics. Some use multiple-choice benchmarks, some use
real specialty cases, and some use clinician ratings. These do not map directly
to DIRECT, INDIRECT, and MISS. For that reason, the comparison below focuses on
shared design points: coordination, memory, and evaluation method.

Compared with MDAgents and MAC, this system uses the same broad idea of
specialised agents working on one clinical task. The difference is that CMADS
uses a fixed LangGraph workflow with parallel Stage~1 execution, a diagnostic
critique loop, and a non-destructive Reviewer-Refiner step. It also adds the
four-tier memory system and evaluates memory with a leakage control.

Compared with ZODIAC and ClinicalLab, a direct accuracy comparison would be
unfair because the cohorts are different. ZODIAC uses real cardiology data.
ClinicalLab uses real cases across eleven departments. This thesis uses
synthetic Synthea patients across several disease groups. The strength of this
setup is control: the same patients, prompts, and evaluator can be reused to
study design choices such as memory and model choice.

Compared with RareAgents, this work supports a similar lesson: workflow and
supporting tools can matter as much as the base model. RareAgents showed that
an open-source model with memory and tools can beat GPT-4o on rare-disease
diagnosis. In this thesis, GPT-OSS-120B inside the seven-agent workflow
outperformed the locally served Med42-70B model on the controlled subset. The
additional point here is the leakage-controlled memory comparison, which is not
usually reported in memory-augmented clinical agent papers.

Bedi et al.'s Optimisation Paradox is also relevant
\cite{Bedi2025OptParadox}. Their work shows that combining individually strong
agents does not guarantee a strong clinical system. The results here support
the same practical message: the workflow, handoffs, review step, and memory
control are part of the system's performance, not secondary details.

\section{Qualitative Case Walkthroughs}
\label{sec:results_qualitative}
% ─────────────────────────────────────────────────────────────────────────────

This section gives three short examples from the saved run files. The aim is
to show what the tables mean at patient level. The examples cover one DIRECT
case, one INDIRECT case, and one MISS.

\paragraph{Case~1 -- DIRECT match after review.}
Patient \texttt{7449ec96} had the target disease
\textit{Essential hypertension}. The first Diagnostic Reasoning output placed a
possible medication-induced electrolyte disturbance first, with essential
hypertension lower in the differential. The Clinical Reviewer judged this as
mis-ranked: the blood pressure pattern, obesity, and pre-diabetes gave stronger
support for primary hypertension than for an unconfirmed diuretic effect. The
Refiner changed the final primary diagnosis to \textit{Essential (primary)
hypertension}. The evaluator marked this as DIRECT at rank~1. The Treatment
Planner then generated a NICE NG136-based plan for hypertension, including
ramipril initiation, renal-function and potassium monitoring, blood-pressure
follow-up, and pregnancy/ethnicity checks before prescribing. This case shows
the value of keeping the reviewer and refiner separate: the system corrected
its first ranking before the final answer was saved.

\paragraph{Case~2 -- INDIRECT match with a related cardiac diagnosis.}
Patient \texttt{68089d6c} had the target disease
\textit{Ischemic heart disease}. The memory step found one previous DIRECT case
that passed the quality filter. The final primary diagnosis was still
\textit{Obstructive jaundice}, because the strongest evidence was a marked
bilirubin elevation and missing abdominal imaging. However, the differential
also included \textit{Heart-failure-related hepatic congestion} at rank~2. The
evaluator marked the case as INDIRECT because cardiac hepatopathy can be a
consequence of heart failure and ischemic heart disease. This example is useful
because it shows that the system can keep a related cardiovascular explanation
in the differential, but the top diagnosis may still follow the most obvious
laboratory abnormality.

\paragraph{Case~3 -- MISS where the target was not recovered.}
Patient \texttt{4fe0fcd1} had the target disease
\textit{Ischemic heart disease}. The Diagnostic Reasoning output first focused
on resistant hypertension. The reviewer then pushed the case toward
\textit{Obstructive sleep apnea} as a likely secondary driver of hypertension,
and the Refiner kept obstructive sleep apnea as the final primary diagnosis.
The evaluator marked the case as MISS because none of the top five diagnoses
were a direct or indirect match for ischemic heart disease. This failure shows
a common weakness in the pipeline: known cardiovascular history can be treated
as background context instead of being carried forward as an active diagnostic
candidate.

\section{Doctor-Facing Dashboard and Clinical Expert Review}
\label{sec:results_dashboard_review}
% ─────────────────────────────────────────────────────────────────────────────

The dashboard is important because it turns the saved JSON outputs into a form
a doctor can inspect. It shows the patient case, agent reasoning, retrieved
guidelines, memory use, and final diagnosis without forcing the reviewer to
read raw files.

\subsection{Dashboard walkthrough}
\label{subsec:results_dashboard}

The system has two review interfaces. The Streamlit dashboard at
\texttt{portal/dashboard.py} is used during development to inspect cohort
metrics and per-patient outputs. The React + FastAPI doctor console at
\texttt{doctor\_console/} is the clinician-facing version. It does not show the
hidden ground truth. Instead, it shows the agent chain, retrieved evidence,
final diagnosis, and similar prior cases.

The doctor console is organised around three views. The first view is the
patient list, where cases can be filtered by match status and basic patient
features. The second view is the assessment page for one patient. It shows the
ranked differential, the final diagnosis, treatment-plan summary when
available, and the saved outputs from each agent. The third view is the agent
flow. It follows the seven stages of execution and lets the reviewer inspect
the output of a selected agent without opening JSON files. This makes the
pipeline easier to explain in a viva or clinician review session, because the
reviewer can move from the patient record to the agent reasoning and then to
the final result in one screen.

The vector-search panel is especially important. It shows the top-$K$ similar
prior patients from case-based memory, ranked by BioLORD-2023 similarity. The
doctor can see their outcomes and evidence patterns. This makes memory use
inspectable. If memory affects the differential, the reviewer should be able to
see which prior cases influenced it.

\subsection{Clinical expert review}
\label{subsec:results_expert}

The clinical expert review has not been completed yet, so this thesis does not
claim clinician-validated accuracy. The review protocol is included because it
defines how the doctor console should be assessed before submission or future
deployment.

\paragraph{Method.}
The reviewer will be shown ten patient cases from the evaluated cohort:
three DIRECT cases, three INDIRECT cases, two MISS cases, and two DIRECT cases
with treatment plans. For each case, the reviewer will see the doctor console
assessment view, including the ranked differential, reasoning summary,
retrieved NICE guideline chunks, and similar-past-cases panel. The reviewer
will not see the Synthea ground truth or the evaluator verdict. Each case will
be scored on four dimensions from 1 to 5, where 1 means unsafe or misleading
and 5 means clinically sound.

\paragraph{Scoring dimensions.}
\begin{itemize}
\item \textbf{Diagnostic plausibility} --- is the primary diagnosis a
  reasonable candidate given the presented evidence?
\item \textbf{Differential completeness} --- does the ranked
  differential cover the conditions a clinician would consider?
\item \textbf{Reasoning transparency} --- is the agents' reasoning
  chain inspectable and clinically intelligible?
\item \textbf{Treatment-plan safety} --- for DIRECT cases that produced
  a treatment plan, does the plan avoid contraindications and align
  with the cited NICE guideline?
\end{itemize}

\paragraph{Planned reporting.}
The review should be reported as a small table with the mean score for each
dimension and the number of cases scoring 4 or 5. Free-text comments should be
grouped into practical themes, such as unsafe treatment advice, missing
differential diagnoses, unclear reasoning, or useful memory explanations. Any
clinician comments must be kept separate from the LLM-as-judge results, because
they measure different things.

\section{Discussion and Limitations}
\label{sec:results_discussion}
% ─────────────────────────────────────────────────────────────────────────────

The results show that the system can usually place the target disease, or a
closely related disease, in the differential diagnosis. The combined found rate
is 88\%, and the correct or related condition is ranked first in 61\% of found
cases. The pipeline also completed without any full patient-run aborts. This
supports the main design choice of the thesis: a coordinated workflow of
specialised agents is more inspectable and reliable than asking one model to do
the whole task in one call.

The memory result needs careful reading. Multi-level memory did not improve the
DIRECT rate. Instead, it reduced MISS cases and increased INDIRECT cases. This
means memory helped the system notice related diagnoses, but it also made the
primary diagnosis less precise. This may still be useful in a dashboard where a
doctor reads the full differential. It would be less useful in a system where
the first diagnosis automatically drives the next action.

The model comparison also matters for practical use. GPT-OSS-120B through Groq
was both more accurate and much faster than Med42-70B through local Ollama on
the tested subset. In a multi-agent pipeline, every extra model call adds time,
so inference speed is not a minor implementation detail. It affects whether the
system can be used interactively.

The results have clear limits. All patients are synthetic and come from Synthea.
The detectability verifier selects cases where the target disease is visible in
the available data, so the cohort is cleaner than real EHR data. Real patient
records would include more missing values, noisier histories, and more complex
comorbidities. Some disease families, especially type-2 diabetes and chronic
congestive heart failure, have small counts, so their per-family percentages
should not be overinterpreted. The memory comparison is also limited in size and
should be repeated on a larger and more balanced cohort. Finally, this is a
research prototype, not a deployable medical device. The dashboard is intended
to support review by a clinician, and the clinician remains the decision maker.
