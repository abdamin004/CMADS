\section{System Architecture Overview}
\label{sec:methodology_overview}
% ─────────────────────────────────────────────────────────────────────────────

This chapter explains how the Clinical Multi-Agent Decisioning System
(CMADS) was built. The system is first shown as a set of simple black boxes,
then each box is opened in the same order. Figure~\ref{fig:system_architecture}
shows the top-level flow: Synthea patient generation, case filtering, Gold
case construction, the LangGraph multi-agent system, and the doctor-facing
dashboard. Inside the multi-agent system are the common agent blueprint,
shared memory, NICE guideline retrieval, and saved run outputs.

\paragraph{Reproducibility.} All source code, agent prompts, and saved
run artefacts are released as the open-source CMADS implementation.
Throughout this chapter and Chapter~\ref{chap:results}, components are
referred to by name (e.g.\ ``the detectability verifier'', ``the
persisted execution trace'') rather than by file path; the exact
locations live in the repository's \texttt{README.md} for readers who
want to inspect or re-run a step. Pinned versions for the empirical
results reported in Chapter~\ref{chap:results}: LangGraph 0.6.x,
\texttt{dbt-core} 1.8.x, Synthea release 3.4, BioLORD-2023
(HuggingFace \texttt{FremyCompany/BioLORD-2023}), Qdrant 1.13.x.

\section{Synthetic Data Generation and Case Filtering}
\label{sec:dataset}
% ─────────────────────────────────────────────────────────────────────────────

This section explains the first three boxes in
Figure~\ref{fig:system_architecture}: Synthea generation, deterministic case
filtering, and Gold case construction. Figure~\ref{fig:data_pipeline}
summarises how raw records become the JSON files passed to the agents.

\begin{figure}[!htbp]
\centering

\includegraphics[width=0.98\textwidth]{images/ch3_data_pipeline.png}
\caption{Synthetic data generation and filtering pipeline. Synthea produces

\label{fig:data_pipeline}

\subsection{Synthea Generation}
The patient records are produced by \textit{Synthea}, an open-source
rule-based patient simulator from MITRE \cite{Walonoski2018Synthea}.
Synthea uses state-machine disease
models informed by public health data and exports records in FHIR R4 format.
It was chosen for two reasons. First, it gives a ground-truth label for the
conditions it creates, which is needed for the LLM-as-Judge evaluation in
Section~\ref{sec:evaluation}. Second, the data is fully synthetic, so the
project can be reproduced without using protected patient information.

\subsection{Target-Cohort Filtering}
\label{sec:cohort_filtering}
A cohort of 1{,}000 patients was generated by Synthea. A deterministic
filter then selected patients from the target disease groups: ischemic
heart disease, congestive heart failure, essential hypertension, diabetes
mellitus type 2, chronic kidney disease stages 2 and 3, end-stage renal
disease, and metabolic syndrome X. A patient was kept only if there were
at least three encounters and five laboratory observations before the
target diagnosis date. This gives the agents enough earlier evidence to
reason from while keeping the target diagnosis itself hidden. From the
1{,}000 patients carried forward into the verification stage, the
LLM-based detectability gate
(Section~\ref{sec:llm_verifier}) returned \texttt{VERDICT~=~YES}
for 428 cases and a confidence score from 0 to 100 for each; the
$\geq 80$~confidence threshold restricts the verified cohort to
\textbf{270 patients}, persisted as
\texttt{data/gold/cohort\_verified.json}. The principal paired
evaluation reported in Chapter~\ref{chap:results} draws a balanced
160-patient subset from this verified cohort to support the paired
multi-level memory A/B; the remaining patients stay available for
the detectability sensitivity analysis and the single-LLM controlled
baseline reported in Sections~\ref{sec:results_detectability_sensitivity}
and~\ref{sec:results_single_llm} respectively.

\paragraph{Scope of the eight families.}
The eight disease families above are the scope of the evaluation
\emph{cohort}, not of the system. The pipeline is disease-agnostic by
design: the agents read free-text chart and lab content, emit
free-text differentials, and the LLM judge scores any candidate
phrasing against any ground-truth diagnosis. The eight families
were chosen because Synthea's generation module produces longitudinal
records with consistent pre-diagnosis signal for these cardiometabolic
conditions; rarer presentations (e.g.\ malignancies, autoimmune
diseases, paediatric and obstetric cases) either do not appear in
Synthea or appear without enough pre-diagnosis evidence for the
detectability gate to admit them. Extending the cohort to a new
disease family is a data-availability question --- supply Gold-layer
patients carrying that family's typical evidence pattern --- not a
re-architecture: the agents, prompts, memory subsystem, and judge
require no changes.
The remaining patients were saved for audit but not run through the
agent pipeline; a subset of the immediately rejected band (confidence
60--79) is used in the detectability-gate sensitivity analysis reported
in Section~\ref{sec:results_detectability_sensitivity}.

\subsection{LLM-Based Detectability Verifier}
\label{sec:llm_verifier}

The encounter and lab-count filters are useful but not sufficient. Synthea
can label a patient with a disease even when the pre-diagnosis record
contains weak evidence: an end-stage renal disease patient may have
normal creatinine, or a diabetes patient may have glucose values inside
the reference range. The label is still valid ground truth, but the case
may not be diagnosable from the data the agents are allowed to see.

A second LLM-based gate is therefore applied before a patient enters
the multi-agent pipeline. The verifier
(\texttt{pipeline/lab\_verifier\_llm.py}) builds a short clinical
summary --- demographics, conditions, medications, risk scores, recent
labs, critical flags, vital signs --- and asks the four questions in
Table~\ref{tab:verifier} using the Synthea target disease as the
reference. It returns four fields: \texttt{VERDICT} (YES or NO),
\texttt{CONFIDENCE} from 0 to 100, an \texttt{EVIDENCE} list, and a
short \texttt{REASONING} sentence. Only patients with
\texttt{VERDICT~=~YES} and \texttt{CONFIDENCE~$\geq$~80} are admitted;
rejected patients are saved for audit but are not run through the
agent pipeline.

The verifier and the LLM-as-Judge evaluator
(Section~\ref{sec:evaluation}) both default to Qwen3-32B via
\texttt{get\_evaluator\_llm()}; the reasoning agents run on a
separate model (GPT-OSS-120B). The detectability-gate sensitivity
analysis in Section~\ref{sec:results_detectability_sensitivity}
measures how much of the headline DIRECT rate depends on this gate.

\begin{table}[!htbp]
\centering
\caption{Detectability-verifier prompt structure.}
\label{tab:verifier}
\footnotesize
\begin{tabular}{@{}p{34mm}p{100mm}@{}}
\toprule
\textbf{Verifier question} & \textbf{What the LLM is asked to check} \\
\midrule
Q1 -- Lab consistency      & Are any lab values abnormal in a way consistent with the target disease (e.g.\ raised HbA1c for diabetes, elevated creatinine for ESRD)? \\
Q2 -- Medication signal    & Do any active medications suggest the target disease (e.g.\ furosemide for CHF, metformin for diabetes)? \\
Q3 -- Condition / risk     & Do any other recorded conditions or risk factors strongly point to the target disease? \\

\bottomrule
\end{tabular}
\end{table}

This two-stage filter (deterministic eligibility + LLM detectability)
produces the 160-patient cohort used throughout
Chapter~\ref{chap:results}. The verifier is a data-quality gate only;
it does not see any agent output and does not judge the system's
diagnosis.

\subsection{Gold Case Construction}
\label{sec:gold_construction}

The raw FHIR output passes through a four-layer medallion data lake
(also visible in Figure~\ref{fig:data_pipeline}, steps~2--7). Each
layer is responsible for a single transformation, which keeps the
pipeline auditable and lets each step be re-run independently.

\paragraph{Bronze.} Stores the raw FHIR resources as Parquet without
modification. This layer exists so that downstream changes can always
be re-derived from the original Synthea output without re-running
the generator.

\paragraph{Silver.} Converts the FHIR resources to OMOP Common Data
Model v5.4 \cite{OMOPCDMv54} using \texttt{dbt-core} on top of DuckDB.
The OMOP CDM is the canonical schema curated by the OHDSI
collaborative \cite{Hripcsak2015OHDSI} for observational health
research; it normalises codes (RxNorm for drugs, SNOMED for
conditions, and LOINC for labs), so the rest of the pipeline operates
on a stable vocabulary regardless of source format.

\paragraph{Silver\textsuperscript{+}.} Adds clinically derived
features on top of OMOP: lab trends (increasing, decreasing, stable),
estimated glomerular filtration rate from creatinine, BP categorical
labels, glycemic-control classes, and a Charlson comorbidity index.
These features are precomputed because every reasoning agent uses
them, and computing them at agent call time would inflate latency.

\paragraph{Gold.} Assembles three JSON files per patient:
\texttt{ehr\_case.json}, \texttt{lab\_case.json}, and
\texttt{ground\_truth.json}. The first two are what the agents see;
the third is reserved for the LLM Evaluator
(Section~\ref{sec:evaluation}).
Table~\ref{tab:gold_files} summarises the contents and consumers of
each file.

\paragraph{Point-in-time construction.} A single methodology decision
shapes every Gold file: \emph{all data shown to the agents must
predate the target disease's first diagnosis date}. The cutoff is
the \texttt{condition\_start\_date} of the target disease, and any
condition, medication, visit, imaging study, or lab dated on or
after that cutoff is excluded from \texttt{ehr\_case.json} and
\texttt{lab\_case.json}. Without this rule the agents would have the
answer in their input and the task would degenerate into a lookup;
with it, diagnosis is a genuine inference task on the same kind of
incomplete information a clinician sees in practice.

\paragraph{Target disease selection.} A single patient may carry many
synthetic conditions; the Gold assembler picks the most clinically
significant one as the target. Diseases are ranked into four
priority tiers (priority~1: heart failure, neoplasms, ischemic heart
disease, ESRD; priority~2: diabetes, CKD stage~3, aortic valve
disease; priority~3: epilepsy, other CKD, metabolic syndrome;
priority~4: everything else). Within a tier the most recent
diagnosis is selected, which maximises the length of the
pre-diagnosis history available to the agents.

\paragraph{Leakage prevention.} The target disease itself is excluded
from the patient's condition list using its SNOMED code, and a
post-build verification confirms that the target disease name does
not appear anywhere in any \texttt{ehr\_case.json}. Comorbidity
flags that name the target disease (\texttt{has\_chf} for a
heart-failure target, etc.) are masked the same way.

\FloatBarrier

\paragraph{What the system reads per patient.}
Every patient case is structured --- the agents never see free-text
notes, images, or identifiers. The case file splits into two groups.
The \textbf{chart-as-recorded} fields, ingested verbatim from Synthea
/ FHIR, are demographics (age, sex, race, ethnicity), the open problem
list with SNOMED codes and onset dates (target excluded), the active
medication list with class, dose, and start date, the most recent
vitals (BP, HR, weight, SpO$_2$) before the cutoff date, and the
latest values for the key analytes (eGFR, HbA1c, lipid panel,
electrolytes, troponin, etc.)\ with units and dates. The
\textbf{derived} features, computed during Silver+ / Gold-layer
assembly so the diagnostic agents do not re-derive them at inference
time, are critical flags (e.g.\ \texttt{eGFR < 60 $\to$ CKD};
\texttt{HbA1c > 6.5\% $\to$ diabetes}), drug-condition links anchoring
each medication to a plausible indication, Boolean comorbidity flags
(\texttt{has\_dm}, \texttt{has\_htn}, \texttt{has\_ckd},
\texttt{has\_ihd}, \texttt{has\_chf}, \texttt{has\_obesity}), and
standard risk scores where the data permits (ASCVD 10-year,
CHA$_2$DS$_2$-VASc, eGFR~CKD-EPI). The same categories are surfaced
verbatim in the doctor console's \emph{Patient Overview} panel so a
clinician can audit exactly what the agents read for any given
consultation.

\section{Multi-Agent System}
\label{sec:mas_framework}
% ─────────────────────────────────────────────────────────────────────────────

The multi-agent pipeline is run with \textit{LangGraph}~\cite{LangGraph2024}.
Each agent is a node
in a \texttt{StateGraph}, and edges define the order of execution. A shared
\texttt{PipelineState} dictionary moves through the graph and carries patient
data, agent outputs, traces, and memory fields. LangGraph was chosen because
it supports parallel fan-out and fan-in, checkpointing after agent steps, and
reducer-based state updates. These reducers are important because Stage~1 runs
two agents in parallel, so one agent must not overwrite the other agent's
output.

Figure~\ref{fig:agent_pipeline} opens the Multi-Agent System box from
Figure~\ref{fig:system_architecture}. The graph has six clinical stages
plus one memory-consolidation stage. Stage~1 runs the EHR Analyst and Lab
Interpreter in parallel. Stage~2 performs diagnostic reasoning. Stages~3
and 4 review and refine the diagnosis. Stage~5 evaluates it. Stage~6
plans treatment only when the diagnosis is a DIRECT match. Stage~7
consolidates the run into the cross-session memory tiers.

\begin{figure}[!htbp]
\centering
% Exported from thesis/diagrams/chapter3/index.html
\includegraphics[width=0.95\textwidth]{images/ch3_agent_pipeline.png}
\caption[Multi-agent system execution]{Multi-agent system execution order.
Each stage card lists the inference back-end on the right and the agents
executing inside the stage on the bottom. Solid arrows between stages name
the output that flows downstream. The black box on the right represents
the shared memory --- a single \texttt{PipelineState} \texttt{TypedDict}
backed by four memory tiers (working, episodic, semantic, case-based);
every stage reads from and writes to it through dashed bidirectional
arrows, as detailed in Section~\ref{sec:shared_memory}. Stage~6 is invoked in
every run but the Treatment Planning agent emits a clinical plan only for
DIRECT evaluations; the Memory Consolidator runs unconditionally and
writes Tier~2--3 plus, when the run is informative enough, Tier~4.}
\label{fig:agent_pipeline}
\end{figure}

The pipeline comprises six clinical stages plus one memory-consolidation
stage that folds each run's outcome into the cross-session memory tiers
(Section~\ref{sec:consolidation}). The seven stages are summarised below.
\begin{itemize}
  \item \textbf{Stage 1 --- Parallel context extraction:} the EHR Analyst and
  Lab Interpreter run concurrently, each consuming its Gold case file and
  producing a structured clinical summary.
  \item \textbf{Stage 2 --- Diagnostic reasoning:} an adaptive loop generates
  a ranked differential, self-critiques it, and re-ranks for up to three
  rounds or until a confidence threshold of 75\% is reached. The
  Pydantic schema (\texttt{DiagnosticOutput}) requires the differential
  to be non-empty; the prompt requests five candidates and the
  reasoning agent typically returns five, but no schema-level lower
  bound above one is enforced.
  \item \textbf{Stage 3 --- Clinical review:} an adversarial reviewer agent
  independently re-examines the evidence and issues per-diagnosis verification
  flags.
  \item \textbf{Stage 4 --- Diagnostic refinement:} the outputs of Stages~2
  and 3 are merged into a single final differential.
  \item \textbf{Stage 5 --- Evaluation:} the final differential is compared
  against the Synthea ground truth by an LLM-as-Judge evaluator that assigns
  DIRECT, INDIRECT, or MISS classifications.
  \item \textbf{Stage 6 --- Treatment planning:} the treatment node is invoked
  after evaluation. For DIRECT matches it retrieves relevant NICE guideline
  passages from a Qdrant vector store and assembles a guideline-grounded
  treatment plan; for INDIRECT or MISS outcomes it records a structured skip.
  \item \textbf{Stage 7 --- Memory consolidation:} a non-LLM maintenance node
  folds the run's outcome into the cross-session semantic store (Tier~3) and
  eligible cases into the case-based vector store (Tier~4); see
  Section~\ref{sec:consolidation}.
\end{itemize}

\section{Agent Blueprint}
\label{sec:agent_blueprint}
% ─────────────────────────────────────────────────────────────────────────────

Every agent follows the same internal pattern, shown in
Figure~\ref{fig:agent_blueprint}. The pattern is implemented as a Python base
class. Each subclass supplies its own prompt, schema, and post-processing
logic. This keeps the pipeline easier to debug because every agent uses the
same retry rules, trace format, validation steps, and failure handling.

\begin{figure}[!htbp]
\centering
% Exported from thesis/diagrams/chapter3/index.html
\includegraphics[width=0.98\textwidth]{images/ch3_agent_blueprint.png}
\caption{Generic agent blueprint. Every agent follows the same path:
Input~Gate~$\to$~Prompt Assembler~$\to$~LLM Invocation~$\to$~Output
Parser~$\to$~Output Gate. The Input Gate reads upstream data, the Prompt
Assembler adds any relevant memory, the LLM returns the raw answer, and the
Output Gate writes the validated result. Memory access goes through one
\texttt{MemoryManager} interface.}
\label{fig:agent_blueprint}
\end{figure}

The five stages of the blueprint are as follows.
\begin{enumerate}
  \item The \textbf{Input Gate} checks that required upstream data exists and
  matches its Pydantic schema. If validation fails, the agent records a
  structured error in \texttt{execution\_\allowbreak trace} and stops cleanly.
  \item The \textbf{Prompt Assembler} constructs the LLM prompt from a
  versioned YAML template, substituting the validated upstream outputs.
  Keeping prompts in YAML instead of hard-coded Python makes prompt changes
  easier to track.
  \item The \textbf{LLM Invocation} layer dispatches the prompt to the
  configured language model through the provider-agnostic adapter
  (Section~\ref{sec:llm_config}). Every call is wrapped in an exponential
  back-off retry policy (up to three attempts); a slow-call warning is
  logged when an individual call exceeds the configured threshold, and
  the outer per-agent budget enforces termination at the agent level.
  \item The \textbf{Output Parser} converts the raw LLM response into a
  Pydantic v2 object and applies JSON repair rules for common formatting
  failures.
  \item The \textbf{Output Gate} applies final validation before writing to
  shared memory. For example, the Diagnostic Reasoning gate requires a
  non-empty differential and is paired with a prompt that instructs the
  agent to return at least three candidates --- the Pydantic schema
  does not enforce a minimum above one, but the agent's prompt and the
  downstream Reviewer-Refiner stages assume a populated top-five
  list. The Treatment Planning gate is, at the level of code, a Pydantic
  schema validator: it enforces that a structured plan is returned and
  that downstream fields parse correctly. The grounding requirement ---
  that medications and procedures cite the retrieved NICE passages ---
  is enforced prompt-side by the Treatment Planning prompt, not by a
  post-hoc retrieval-support check; a programmatic support check is identified
  as future work in Chapter~\ref{chap:conclusion}.
\end{enumerate}

\subsection{EHR Analyst Agent}
\label{sec:agent_ehr}
The \textbf{EHR Analyst} is the first Stage-1 agent. It reads
\texttt{ehr\_case.json} and produces a structured summary of demographics,
active conditions, medications, history, and prior encounters. The prompt asks
the agent to cite the record behind each claim so later agents and reviewers
can check where the information came from. Internally, the agent uses three
LLM calls (Figure~\ref{fig:agent_ehr_flow}): an \textit{analysis} call, a
\textit{structure} call that fills JSON fields, and a \textit{review} call
that checks the structured output.

\FloatBarrier
\subsection{Diagnostic Reasoning Agent}
\label{sec:diagnostic_reasoning}
\label{sec:agent_diag}
The \textbf{Diagnostic Reasoning} agent is the Stage-2 agent that creates
the ranked differential diagnosis.

Throughout this subsection a \emph{prior} refers to a past patient case
retrieved from Tier-4 case-based memory whose clinical features are
similar to the current patient's. The diagnosis recorded for that
retrieved case acts as a Bayesian-style starting point for the current
reasoning, in the way a clinician's recall of a similar patient anchors
their first impression. A prior is treated as \emph{strong} only when the
retrieved case clears both a similarity threshold and a quality threshold
(the past case must itself have been a DIRECT match with high evaluator
confidence); otherwise the agent acts as if no prior were available.
The full case-based memory mechanism is described later in
Section~\ref{sec:multilevel_memory}.

The agent has two modes. If memory is disabled, or if no strong prior is
found, it uses an \textit{adaptive critique loop}. If Tier-4 case-based
memory returns a strong prior case, it uses a \textit{three-phase split}
to use the prior without blindly following it. Both modes are limited to
three rounds.

In the adaptive loop, the agent first combines the EHR and lab summaries,
then proposes at least three diagnoses, ranks them, and critiques the result.
The loop stops when confidence reaches 75 or after three rounds. This design
follows the idea that difficult cases may need more than one reasoning pass
\cite{Shang2025DynamiCare,Kim2024MDAgents}.

\paragraph{Three-phase split.}
When memory returns a strong prior, the agent runs three rounds
(Figure~\ref{fig:agent_diag_flow}). \textit{Round~A} shows the prior case
and asks the agent to use it only when the current evidence supports it.
\textit{Round~B} hides the prior and asks the agent to reason from the current
patient only. \textit{Round~C} compares both rounds. If they agree, the
diagnosis is kept. If they disagree, Round~B is preferred unless Round~A has
clear supporting evidence in the current patient. This clean-room round is
included to reduce anchoring on retrieved cases \cite{Wang2025Catfish}.

\FloatBarrier
\subsection{Clinical Reviewer Agent}
\label{sec:agent_reviewer}
The \textbf{Clinical Reviewer} is the Stage-3 agent. It re-checks the evidence
and the diagnostic differential. Its prompt asks it to challenge the primary
diagnosis, suggest missed alternatives, and identify possible bias. This is
meant to avoid \textit{silent agreement}, where agents appear to review each
other but simply accept the first answer \cite{Wang2025Catfish}.

\subsection{Diagnostic Refiner Agent}
\label{sec:agent_refiner}
The \textbf{Diagnostic Refiner} is the Stage-4 agent. It combines the
Diagnostic Reasoning output with the Clinical Reviewer critique. When both
agents agree, it mainly cleans terminology and adjusts ranks. When they
disagree, it uses the review flags: \textit{verified} diagnoses are promoted,
\textit{refuted} diagnoses are demoted, and \textit{uncertain} diagnoses keep
their position. The final output is written to
\texttt{agent\_outputs.final\_diagnosis}. With memory enabled, the Refiner
also reads the Tier-2 timeline and relevant Tier-3 disease priors.
Figure~\ref{fig:agent_refiner_flow} shows the merge flow.

\FloatBarrier
\subsection{LLM Evaluator Agent}
\label{sec:agent_eval}
The \textbf{LLM Evaluator} is the Stage-5 agent. It compares the final
differential with the Synthea ground truth in \texttt{ground\_truth.json}.
It uses a different model configuration from the reasoning agents so that the
same model is not both generating and judging the answer. The evaluator returns
DIRECT, INDIRECT, or MISS, as defined in Section~\ref{sec:evaluation}.

\FloatBarrier
\subsection{Treatment Planning Agent}
\label{sec:agent_tx}
The \textbf{Treatment Planning} agent is the Stage-6 node. It runs after
evaluation, but it writes a treatment plan only when the evaluator returns
DIRECT. For INDIRECT or MISS outcomes, it writes a structured skip so that
the run remains traceable without giving treatment advice for an uncertain
diagnosis. For DIRECT cases, it retrieves the relevant NICE guideline
passages from Qdrant and passes them to the LLM together with the final
diagnosis and the patient's structured record.

\paragraph{Structured output.} The agent emits a typed JSON object
(Pydantic schema \texttt{TreatmentOutput}). The object holds the NICE
guideline identifier (such as NG106 or NG136) and four content
sections:

\begin{itemize}
  \item \textbf{Prescribed medications} --- each entry carries drug name,
        class, dose, duration, clinical purpose, the supporting NICE
        reference, and a line label (\textit{first-line},
        \textit{second-line}, or \textit{additional}).
  \item \textbf{Interaction checks} --- pairwise interactions between
        proposed drugs and the patient's current medications, each with a
        severity (mild, moderate, severe) and a recommended action.
  \item \textbf{Contraindications} --- drugs that should \emph{not} be
        given to this specific patient, with the reason and an
        alternative.
  \item \textbf{Assumptions and warnings} --- explicitly flagged below.
\end{itemize}

\paragraph{Warnings and assumptions surfaced to the doctor.} A NICE
guideline is written for the data a clinician would normally have at
hand, but a Synthea (or real-world) record often lacks specific fields.
Rather than silently substituting defaults, the agent is required to
list \emph{every} assumption it was forced to make. The prompt instructs
it to write one warning per missing data item that would otherwise have
gated a recommendation. Typical entries include:

\begin{itemize}
  \item ``eGFR unknown --- assumed normal for ACE-inhibitor dosing''
  \item ``Allergy status unknown --- cannot verify drug safety''
  \item ``QRISK not calculated --- NICE NG181 requires it for the
        statin decision''
  \item ``LVEF unknown --- cannot confirm HFrEF vs HFpEF for drug
        selection''
  \item ``Liver function missing --- cannot verify statin safety''
  \item ``Potassium unknown --- cannot verify MRA / spironolactone
        safety''
\end{itemize}

These warnings, together with any contraindications and severe
interactions, are written into the same JSON object and rendered
verbatim in the clinician dashboard alongside the medication list. The
intent is that the doctor never sees a recommendation without also
seeing what the agent did not know, so that calibrated trust
\cite{Bedi2025OptParadox} can be exercised at the point of use rather
than retrospectively. Whether this surfacing strategy actually changes
clinician behaviour remains an empirical question for prospective
clinician-in-the-loop deployment, identified as future work in
Chapter~\ref{chap:conclusion}.

\section{Shared Memory Design}
\label{sec:shared_memory}
% ─────────────────────────────────────────────────────────────────────────────

Agents communicate through a typed shared state called
\texttt{PipelineState}. On top of this state, the system adds a four-tier
memory design inspired by CoALA \cite{Sumers2024CoALA}. The base state handles
one patient run and merges agent updates safely. The four memory tiers then add
scratch space, a run-level event trail, disease-level summaries across runs,
and case-based recall from previous patients.

% ─────────────────────────────────────────────────────────────────────────────
\subsection{Base layer: \texttt{PipelineState}}
\label{sec:pipeline_state}
% ─────────────────────────────────────────────────────────────────────────────

Each field of \texttt{PipelineState} is a separate namespace with a reducer
function. The reducer defines how partial updates are merged. This matters
because Stage~1 runs two agents in parallel. If both write during the same
step, the reducer controls the merge instead of leaving the result to
last-writer-wins behaviour.

The shared state is divided into seven namespaces:

\begin{itemize}
  \item \texttt{patient\_context} --- the Gold case object, written once by
  the orchestrator and read by all agents.
  \item \texttt{agent\_outputs} --- a dictionary with one slot per agent,
  using a write-own / read-upstream access pattern. The merge reducer
  ensures that parallel Stage-1 agents never overwrite each other.
  \item \texttt{execution\_trace} --- an append-only invocation log
  recording the status, duration, and error of every agent run.
  \item \texttt{scratchpad} --- per-agent dictionaries; in the present
  design this slot is repurposed as the working-memory tier
  (Section~\ref{sec:tier1}).
  \item \texttt{conflicts} --- an append-only list reserved for an
  orchestrator-level diff engine; not currently written by any agent and
  retained for forward compatibility.
  \item \texttt{session\_memory} --- append-only list of typed
  \texttt{SessionEvent} dictionaries that constitute the episodic-memory
  timeline for the current run.
  \item \texttt{session\_summary} --- per-agent one-line digest with a
  merge reducer, intended as a lightweight scoreboard for downstream
  routing logic.
\end{itemize}

% ─────────────────────────────────────────────────────────────────────────────
\subsection{Multi-level memory subsystem}
\label{sec:multilevel_memory}
% ─────────────────────────────────────────────────────────────────────────────

The base shared state is useful, but it has two limits. Downstream agents see
only the final structured output of earlier agents, not the reasoning trail.
Also, nothing is carried from one patient run to another. The multi-level
memory subsystem addresses these two limits while keeping the same reducer
rules. All tiers are accessed through one \texttt{MemoryManager}, and the
whole subsystem can be turned on or off with the \texttt{MEMORY\_ENABLED}
environment flag. Figure~\ref{fig:multilevel_memory} shows the design.

\begin{figure}[!htbp]
\centering
% Exported from thesis/diagrams/chapter3/index.html
\includegraphics[width=0.98\textwidth]{images/ch3_multilevel_memory.png}
\caption{Four-tier multi-level memory subsystem layered on the LangGraph
state. All agents access memory through the \texttt{MemoryManager} facade:
Tier~1 and Tier~2 support per-run reasoning and traceability, while Tier~3
and Tier~4 persist cross-session semantic and case-based information.
Stage~7 writes the durable tiers only after patient-facing outputs are
produced. NICE guideline retrieval remains external reference knowledge,
not learned memory.}
\label{fig:multilevel_memory}
\end{figure}

% ── Tier 1 ───────────────────────────────────────────────────────────────────
\paragraph{Tier 1 --- Working memory.}
\label{sec:tier1}
Tier~1 is per-agent scratch space for a single invocation. It lives in
\texttt{scratchpad[agent\_id]}. The Diagnostic Reasoning agent uses it during
its critique loop to keep round confidence values and short critique notes.
This avoids reparsing earlier free-text responses. Tier~1 is cleared at the
start of each invocation and is not visible to other agents.

% ── Tier 2 ───────────────────────────────────────────────────────────────────
\paragraph{Tier 2 --- Episodic memory.}
\label{sec:tier2}
Tier~2 is a typed event timeline for one patient run. It is written to
\texttt{session\_memory} through an append reducer. Each entry is a validated
\texttt{SessionEvent} with an event type, agent id, one-line summary, and
structured payload. The Clinical Reviewer reads the critique events when
checking the Diagnostic Reasoning output. The Diagnostic Refiner reads the full
timeline before producing the final differential. The timeline is saved as
\texttt{session\_memory.json} next to \texttt{execution\_trace.json}.

% ── Tier 3 ───────────────────────────────────────────────────────────────────
\paragraph{Tier 3 --- Semantic memory.}
\label{sec:tier3}
Tier~3 stores disease-level statistics across runs in
\texttt{data/gold/memory/semantic\_memory.json}. For each disease, it keeps
DIRECT, INDIRECT, and MISS counts, rank-1 frequency when found, average top
differential probability, and a small set of observed evidence patterns.
Updates are atomic and repeat-safe. Recall is a simple case-insensitive lookup
by disease name. The Diagnostic Refiner and Treatment Planning agent read these
entries as lightweight priors.

% ── Tier 4 ───────────────────────────────────────────────────────────────────
\paragraph{Tier 4 --- Case-based memory.}
\label{sec:tier4}
Tier~4 stores prior patient cases in Qdrant \cite{Qdrant2024}. After a
completed run, the system
builds a short clinical text from demographics, active conditions, medications,
and abnormal labs. This text is encoded into a vector using
BioLORD-2023 \cite{Remy2023BioLORD} --- a biomedical Sentence-BERT
variant \cite{Reimers2019SentenceBERT} fine-tuned on clinical
knowledge-graph signals --- and stored in the
\texttt{patient\_cases} Qdrant collection.
The payload stores the matched diagnosis, match type, rank, confidence, and
evidence patterns. At the start of a new case, the Diagnostic Reasoning agent
retrieves the top-$K$ similar cases ($K=5$ by default) and can use them as
priors. If Qdrant or the embedding model is unavailable, recall returns an
empty list instead of stopping the run.

The NICE guidelines used by the Treatment Planning agent are stored in a
separate Qdrant collection called \texttt{nice\_guidelines}. They are not part
of memory because they are static external reference knowledge, not experience
learned from previous patient runs.

% ─────────────────────────────────────────────────────────────────────────────
\subsection{Memory consolidation node}
\label{sec:consolidation}
% ─────────────────────────────────────────────────────────────────────────────

Tier~3 and Tier~4 are written by a Stage~7 maintenance node. This node runs
after Treatment Planning. It reads the final diagnosis, evaluator verdict, and
patient context. It can write a disease summary to Tier~3 and, when eligible,
upsert the patient case to Tier~4. DIRECT cases are enabled by default for
Tier~4. If one write fails, the other can still succeed, and the trace records
the partial result. This keeps memory failures separate from the patient output
already written by Stages~1--6.

% ─────────────────────────────────────────────────────────────────────────────
\subsection{Access pattern}
\label{sec:memory_access}
% ─────────────────────────────────────────────────────────────────────────────

The per-agent access pattern is summarised on
Figure~\ref{fig:multilevel_memory}: an agent writes only to its own
output slot and to append-only event channels, and cross-session
writes (Tier~3 and Tier~4) are limited to the Stage~7 consolidation
node.

The memory code lives in \texttt{src/memory/}, with one module per tier and a
shared \texttt{MemoryManager} in \texttt{manager.py}. The Stage~7 consolidation
node is implemented in \texttt{src/agents/memory\_consolidator.py}.

\section{Retrieval-Augmented Generation Layer}
\label{sec:rag}
% ─────────────────────────────────────────────────────────────────────────────

Retrieval-Augmented Generation \cite{Lewis2020RAG} combines a learned
retriever over an external document store with a generative model
that conditions on the retrieved passages; in this pipeline it is the
mechanism that lets the Treatment Planning agent ground its
recommendations in NICE guideline text rather than relying on
parametric knowledge alone. Two pieces of the pipeline retrieve from
Qdrant at inference time. The
Diagnostic Reasoning agent draws on Tier-4 case-based memory (described
in Section~\ref{sec:multilevel_memory}) --- past patient cases this
system has previously processed, used as priors for the differential
diagnosis. The Treatment Planning agent draws on the
\emph{external knowledge} corpus described in this section: NICE
clinical practice guideline documents \cite{NICEGuidelines}
authored outside the system.
This separation is deliberate. Diagnosis must be based on the current
patient's evidence and on similarity to past patients only; published
guidelines are kept out of the diagnostic path so that the agents do
not match a guideline-recognised pattern instead of reasoning from the
evidence. Guidelines enter only after the LLM Evaluator has scored
the diagnosis as DIRECT.

The external retrieval corpus contains NICE guideline documents for
the target disease groups. The documents are split into overlapping
chunks of about 400 tokens with 50-token overlap, encoded into
vectors using BioLORD-2023, and stored in Qdrant. Qdrant was used because it
supports filtered retrieval: the Treatment Planning agent can
restrict retrieval to passages tagged with the final diagnosis code,
which reduces the risk of pulling in passages from the wrong
guideline. The same Qdrant deployment holds Tier-4 case-based memory
in a separate collection (\texttt{patient\_cases}), so the two
retrieval paths share infrastructure but never share content.

At inference time, the Treatment Planning agent queries with the
final diagnosis and the top supporting findings. It retrieves the
top five passages, removes duplicates, and inserts them into the
prompt. The prompt asks the model to cite the passage identifier for
each recommendation. The Output Gate (described in
Section~\ref{sec:agent_blueprint}) performs schema validation; the
requirement that medications and procedures appear in the retrieved
passages is enforced prompt-side rather than by a post-hoc
retrieval-support check.

\section{LLM Configuration and Provider Abstraction}
\label{sec:llm_config}
% ─────────────────────────────────────────────────────────────────────────────

All LLM calls go through one provider adapter. The adapter exposes Groq,
OpenAI, Anthropic, Google Gemini, and Ollama through the same
\texttt{get\_llm()} interface. Configuration is read from environment
variables. A separate \texttt{get\_evaluator\_llm()} function is used for the
judge model, so the evaluator can be different from the reasoning model.

Three model configurations were used in this thesis:
\begin{itemize}
  \item \textbf{GPT-OSS 120B} served via the Groq cloud API, used as the
  primary reasoning model.
  \item \textbf{Med42 70B} (\texttt{thewindmom/llama3-med42-70b}), a Llama-3
  checkpoint fine-tuned on clinical text, served locally via Ollama and used
  in the medical-fine-tuning comparison reported in
  Chapter~\ref{chap:results}.
  \item \textbf{Qwen3 32B} served via Groq, used as the LLM Evaluator
  judge and also as the default detectability verifier in
  Section~\ref{sec:llm_verifier} via the shared
  \texttt{get\_evaluator\_llm()} factory. Qwen3 32B is independent of the
  two reasoning models under test, which prevents the judging result
  from being biased by shared training data with GPT-OSS-120B or
  Med42-70B. Because the cohort-admission verifier and the LLM judge
  resolve to the same default model, the headline DIRECT rate carries a
  same-model selection/evaluation coupling on cohort admission and
  judging; the detectability-gate sensitivity analysis in
  Section~\ref{sec:results_detectability_sensitivity} is the explicit
  empirical check on this coupling (see also
  Section~\ref{sec:results_detectability_sensitivity} for the
  rejected-band counterfactual that bounds the coupling's effect).
\end{itemize}

All LLM calls use exponential backoff with at most three attempts. The
adapter logs a structured warning when a single LLM call exceeds 120
seconds but does not, by itself, cancel the call. Per-agent execution is
bounded by an outer 300-second budget that wraps the entire agent
invocation (Input Gate~$\to$~Output Gate) and that the orchestrator uses
to abort a stalled agent without aborting the patient run.

\section{Observability and Trace Inspection}
\label{sec:observability}
% ─────────────────────────────────────────────────────────────────────────────

Observability in a multi-agent clinical system has two distinct
audiences. The engineer rebuilding or extending the pipeline needs to
see every prompt, every retry, and every JSON-parsing failure in
context. The clinician or examiner reviewing a single patient run
needs to see what each agent received, what it returned, and which
hypothesis the Refiner kept against the Reviewer's verified, refuted,
and uncertain flags. CMADS handles these audiences with the same
data, surfaced through two complementary layers --- a local-first
layer that always runs and an external developer-platform layer that
augments it during development and debugging.

\paragraph{Layer 1 --- local persistence (always on).}
Every patient run writes a structured trail to disk and to MongoDB
without any external service. The orchestrator appends one entry per
agent invocation to the \texttt{execution\_trace} reducer channel
(Section~\ref{sec:pipeline_state}): agent identifier, start and end
timestamps, wall-clock duration, terminal status (\texttt{success},
\texttt{partial}, \texttt{error}, or \texttt{skipped}), and a
truncated error string when the agent raised. The per-agent JSON
output written under the patient's result-set directory (and into the
Mongo \texttt{agent\_runs} document) is the corresponding payload.
Together these two artefacts answer ``what happened on this patient,
in what order, for how long, and to what success state'' for every
historical run without re-executing it. The Python
\texttt{structlog}-based JSON-lines logger emits a parallel
per-process log stream so a live or post-mortem investigation of
ad-hoc behaviour (timeouts, JSON-mode fallbacks, repair-pass
activations) can be done from the terminal.

\paragraph{Layer 2 --- LangSmith trace platform (optional, EU-hosted).}
When the operator sets the \texttt{LANGSMITH\_API\_KEY} environment
variable, the LLM adapter auto-enables LangSmith
tracing~\cite{LangSmith2024} against the EU endpoint
(\url{https://eu.api.smith.langchain.com}) under the project
\texttt{cmads-clinical-pipeline}. The trace captures every LLM
invocation issued by every agent (including the diagnostic loop's
multiple rounds and the Reviewer's adversarial pass), the full prompt
text, the raw model response before any JSON-repair work, latency,
token usage where the provider reports it, and any retried call that
exited via the \texttt{json\_validate\_failed} branch. Failures
propagate as exception breadcrumbs attached to the parent span, so
the trace tree shows where in the seven-agent topology a fault
originated rather than only that the patient run aborted. LangSmith
tracing is auto-instrumented through the LangChain integration and
therefore does not require code changes inside each agent.

The two layers are deliberately redundant. The local layer is the
authoritative record for thesis reproducibility and for regulatory
traceability (see Section~\ref{sec:discussion_regulation}), survives
without any external dependency, and is what the doctor-facing
console reads. The LangSmith layer is the developer's microscope ---
useful when an agent's structured output looks wrong and the question
is what the model actually returned before
\texttt{BaseAgent.\_extract\_json\_from\_response} repaired it. The
operator can disable Layer~2 entirely by leaving the API key unset;
no run on the empirical 160-patient cohort depends on LangSmith being
reachable.

\section{Evaluation Framework}
\label{sec:evaluation}
% ─────────────────────────────────────────────────────────────────────────────

The evaluation follows two rules. First, the ground truth should not be
generated by an LLM, because the system being evaluated is already LLM-based.
Synthea provides rule-based disease labels, so it avoids that circularity.
Second, the model that judges the answer should not be the same model that
generated it. For this reason, the reasoning model and judge model are kept
separate.

\subsection{Ground Truth Extraction}
For every Synthea patient, Gold assembly creates a \texttt{ground\_truth.json}
file. It stores the target condition, SNOMED concept, human-readable disease
name, and date of first diagnosis. Only the Stage~5 evaluator reads this file.
Reasoning agents never receive it.

\subsection{LLM-as-Judge Methodology}
The evaluation here follows the LLM-as-a-judge protocol of Zheng et
al.~\cite{Zheng2023JudgeLLM}, in which a strong external model
adjudicates the output of another model against a reference using a
fixed rubric. The LLM Evaluator receives the target disease and the
top five diagnoses from
the final differential. It classifies each candidate as DIRECT, INDIRECT, or
MISS using a fixed rubric, then selects the best match and reports its
rank. Temperature is fixed at zero. The response uses a five-line structured
format parsed by regex. Table~\ref{tab:match_types} summarises the rubric.

\begin{table}[!htbp]
\centering
\caption{Match-type rubric applied by the LLM Evaluator.}
\label{tab:match_types}
\small
\begin{tabular}{@{}p{22mm}p{95mm}@{}}
\toprule
\textbf{Match type} & \textbf{Criterion} \\
\midrule
DIRECT   & The candidate names the same disease as the ground truth, possibly
           under a clinically equivalent synonym (e.g.\ ``Atherosclerotic CVD''
           is a DIRECT match for ``Ischemic heart disease''). \\
INDIRECT & The candidate names a cause, consequence, precursor, or subtype of
           the ground truth (e.g.\ ``CKD stage 4'' is INDIRECT for
           ``End-stage renal disease''). \\
MISS     & The candidate has no clinical connection to the ground truth. \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Metrics}
The primary outcomes reported in Chapter~\ref{chap:results} are the
three match-type rates and a conditional rank metric, supported by
agent-level reliability and latency statistics.
\begin{itemize}
  \item \textbf{DIRECT rate} --- the proportion of patients for which at
  least one diagnosis in the top five is classified as DIRECT.
  \item \textbf{INDIRECT rate} --- the proportion of patients for which
  no diagnosis is DIRECT but at least one is INDIRECT.
  \item \textbf{MISS rate} --- the proportion of patients with no
  DIRECT or INDIRECT match in the top five.
  \item \textbf{Found rate} --- the combined DIRECT plus INDIRECT rate.
  \item \textbf{Rank-1-when-found} --- among patients for whom the
  pipeline returns a DIRECT or INDIRECT match, the proportion for which
  that match is at rank~1. Denominator = DIRECT + INDIRECT;
  numerator = DIRECT (and INDIRECT) cases ranked first. This is the
  rank metric reported in Chapter~\ref{chap:results}; it replaces a
  legacy ``Top-1 direct rate over all patients'' framing.
  \item \textbf{Memory comparison metrics} --- the controlled
  160-patient paired cohort (Section~\ref{sec:results_memory_ab})
  compares DIRECT, INDIRECT, MISS, Found, and Rank-1-within-found
  rates between the single-level and multi-level memory configurations
  on the same patients.
  \item \textbf{Detectability-gate sensitivity} --- a descriptive
  comparison of DIRECT, INDIRECT, and MISS rates on the
  detectability-admitted cohort against an independent sample drawn
  from the rejected band of the verifier
  (Section~\ref{sec:results_detectability_sensitivity}).
  \item \textbf{Agent success rate} --- per-agent, the proportion of
  patients for which the agent terminated without error.
  \item \textbf{Per-patient latency} --- wall-clock time from
  orchestrator invocation to final-diagnosis write.
\end{itemize}

\section{Implementation Stack and Deployment}
\label{sec:env}
% ─────────────────────────────────────────────────────────────────────────────

The experiments used a local Apple Silicon workstation for the data pipeline
and local Ollama runs. GPT-OSS-120B and Qwen3-32B were served through Groq.
Qdrant was used as a managed cloud vector store. Synthea is the only patient
data generator, and its FHIR R4 output passes through the medallion data lake
before the agents run. Figure~\ref{fig:tech_stack} groups the technology stack
by layer.

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.98\textwidth]{images/ch3_tech_stack.png}
\caption[Technology stack]{CMADS technology stack grouped by layer. Synthea is
the sole data source; LangGraph orchestrates the agent graph; the multi-tier

Environment-specific settings, such as model name, Ollama endpoint, prompt
paths, output directory, and checkpoint location, are stored in configuration

process start. This allows the same Gold JSON inputs and LangGraph pipeline to
be rerun without changing the code.

\subsection{Storage layer and scalability}
\label{sec:methodology_storage}

The system uses two persistence layers with different roles. The
\emph{cold} layer is the read-only ground-truth pile: Synthea FHIR
bundles in \texttt{data/bronze/}, the OMOP CDM Silver tables in the
DuckDB file \texttt{data/clinical.duckdb}, and the Qdrant vector
collections that hold the NICE guideline embeddings and the Tier-4
case-based memory. These do not change during agent runs and are not
the throughput bottleneck. The \emph{hot} layer is MongoDB~7, holding
four collections that grow with every patient run: \texttt{agent\_runs}
(one document per \texttt{(result\_set, patient\_uuid)} pair, with one
field per agent envelope), \texttt{patient\_cases} (the Gold-layer
inputs, one document per patient), \texttt{semantic\_memory} (one
document per disease with running counts), and \texttt{derived\_artefacts}
(per-cohort McNemar tables, sensitivity summaries, and similar
analysis outputs).

The choice of MongoDB is motivated by the read pattern of the
Researcher journey rather than by the write throughput of patient
runs. Every visit to the Overview, Memory A/B, Model, or
MAS-vs-single-LLM tab is one or more aggregations across the
160-patient principal cohort (or the wider union of all completed
runs); on the original on-disk JSON layout each page rendered roughly
$\sim$5 thousand file reads, so latency grew linearly with cohort
size. With the four-collection schema and an indexed compound key on
\texttt{(result\_set, patient\_uuid)}, the same KPI tiles are computed
in a single \texttt{\$group} aggregation that completes in tens of
milliseconds. The migration also makes the system ready for
real-EHR replication: the same agent code paths now accept any number
of \texttt{result\_set}s without changing the read code, and the
addition of a sharded MongoDB deployment is a deployment change rather
than a code change.

\paragraph{Write path.}
Agent envelopes are written to Mongo from inside
\texttt{BaseAgent.\_\_call\_\_} using the synchronous PyMongo driver. The
pipeline runs synchronously inside worker threads dispatched by the
runtime, and Motor (the async driver) is event-loop-bound, so the
sync path is the only one that completes reliably from any thread.
The filesystem JSON write that has always existed remains untouched
during a 30-day soak window controlled by the \texttt{USE\_MONGO}
configuration flag: with the flag off the system falls straight back
to the on-disk tree, which is the documented rollback artefact.

\paragraph{Read path.}
The FastAPI backend at \texttt{doctor\_console/backend/app.py} owns
the read path. The aggregation helpers
(\texttt{\_aggregate\_result\_set\_mongo},
\texttt{\_rank\_distribution\_mongo},
\texttt{\_per\_disease\_breakdown\_mongo},
\texttt{\_top\_diagnoses\_mongo}) issue Mongo aggregation pipelines
that coalesce the canon-augmented verdict
(\texttt{agents.evaluation.output\_canon}) over the original
(\texttt{agents.evaluation.output}) via \texttt{\$ifNull}, so the
headline numbers in the Researcher Overview match the corrected
verdicts reported in Section~\ref{sec:results_e2e} without a separate
post-processing pass. The per-patient detail endpoint
(\texttt{/api/results/...}) keeps reading from disk because it needs
the rich agent narrative and shared-memory summary that only the
filesystem layout currently materialises.

\paragraph{API.}
The doctor console talks to the backend over a small REST surface
served by FastAPI: \texttt{/api/stats/overview} for the headline
KPIs, \texttt{/api/comparisons/memory-ab},
\texttt{/api/comparisons/model}, and
\texttt{/api/comparisons/mas-vs-single-llm} for the three
comparison tabs, \texttt{/api/patients} for the cohort sidebar,
\texttt{/api/results/\{result\_set\}/\{patient\_uuid\}} for the
per-patient drill-down, and a small streaming pair
(\texttt{POST /api/runs}, \texttt{GET /api/runs/\{task\_id\}/stream})
for the Doctor (runtime) journey. The streaming endpoint pushes the
agent-flow state via Server-Sent Events so the runtime view can
``light up'' the active stage and stream each agent's narrative as it
completes, without polling. FastAPI's lifespan handler binds Beanie
to the configured database at startup when
\texttt{USE\_MONGO} is enabled; with it disabled the same handlers
fall back to filesystem-scanning helpers, preserving the rollback
contract.

\paragraph{Patient builder.}
The Doctor (\emph{Assist me}) journey hosts a second tab,
\emph{Build / clone a patient}, that lets the clinician author a case
from scratch (demographics, conditions, medications, vitals, recent
labs) or clone a verified Gold-layer patient as a starting point and
edit any field before running the pipeline. A \emph{Smart Import} flow
inside the Recent labs tab extracts structured lab values from pasted
text, an uploaded PDF or FHIR JSON file, or a photo of a lab slip
(parsed with Gemini~2.5~Flash), so an arbitrary panel can be entered
without retyping every numeric result. The builder lives entirely
inside the Doctor journey --- the Researcher journey does not surface
it. Builder runs are written to a separate
\texttt{mas\_results\_test} cohort so ad-hoc cases never contaminate
the research statistics shown to the reviewer.

\section{End-to-End Execution Pipeline}
\label{sec:pipeline_e2e}
% ─────────────────────────────────────────────────────────────────────────────

Algorithm~\ref{alg:e2e} summarises one full patient run. The pipeline can be
started from the command line for batch runs or through the doctor console's
Doctor (runtime) journey for interactive review.

\begin{algorithm}[ht]
\caption{End-to-end processing of a single patient.}
\label{alg:e2e}
\begin{algorithmic}[1]
\STATE Load Gold case objects \texttt{ehr\_case.json} and \texttt{lab\_case.json}
\STATE Initialise \texttt{PipelineState} with patient context and empty output slots
\STATE \textbf{Stage 1 (parallel):} invoke EHR Analyst and Lab Interpreter concurrently
\STATE \textbf{Stage 2:} invoke Diagnostic Reasoning; repeat critique round until
       confidence $\geq 75$ or three rounds executed
\STATE \textbf{Stage 3:} invoke Clinical Reviewer with Stage 1 and Stage 2 outputs
\STATE \textbf{Stage 4:} invoke Diagnostic Refiner to merge Stages 2 and 3
\STATE \textbf{Stage 5:} invoke LLM Evaluator to classify the final diagnosis
       against the Synthea ground truth
\STATE \textbf{Stage 6:} invoke Treatment Planning; DIRECT matches use RAG over
       Qdrant, while INDIRECT or MISS outcomes produce a structured skip result
\STATE \textbf{Stage 7:} invoke Memory Consolidation; when enabled, update
       Tier~3 semantic memory and eligible Tier~4 patient cases
\STATE Persist \texttt{agent\_outputs} and \texttt{execution\_trace} to MongoDB
       (one document per agent stage, keyed by \texttt{patient\_uuid})
\end{algorithmic}
\end{algorithm}

After each patient, the system writes all agent outputs, the execution trace,
and the evaluation result to MongoDB. These records can be reopened in the
doctor console (Researcher journey) or analysed later without rerunning the
agents.
