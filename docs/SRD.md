**1. Introduction**

**1.1 Purpose**

This System Requirements Document (SRD) specifies the functional and non-functional requirements for a multi-agent AI system designed to support clinical decision-making. The system operates entirely on synthetic patient data generated by Synthea, an open-source patient simulator that models realistic patient lifespans through rule-based state transition machines and Monte Carlo simulation. Synthea is the single source of truth for all patient data in the system. This Synthea-generated data is processed through a coordinated pipeline of specialised AI agents that produce diagnostic assessments and treatment plans for clinician review.

The document serves as the authoritative requirements baseline for the bachelor thesis project. It defines what the system shall do and the constraints under which it shall operate, without prescribing implementation details except where architectural decisions are requirements in themselves (e.g., the use of a multi-agent orchestration pattern).

**1.2 Scope**

The system, referred to throughout this document as the Clinical Multi-Agent Decisioning System (CMADS), encompasses two major subsystems:

-   **Data Pipeline Subsystem:** Responsible for ingesting Synthea-generated synthetic patient data (the sole data source for the entire system), transforming it through Bronze, Silver, Silver+, and Gold layers, and producing the structured case files consumed by the agent pipeline. This subsystem is a supporting component and is not the primary focus of this thesis.

-   **Multi-Agent Pipeline Subsystem:** The core contribution of this thesis. An orchestrator-driven pipeline of specialised AI agents that collaboratively analyse patient data, reason about diagnoses and treatments, and produce a consolidated clinical decision report. This subsystem is the primary subject of the requirements specified herein.

The system operates exclusively on synthetic patient data produced by Synthea. No real patient data is used at any stage. All downstream data layers (Silver, Silver+, Gold) are derived entirely from Synthea's output. The system is intended as a research prototype and is not designed, validated, or approved for use in real clinical environments.

**2. Overall Description**

**2.1 Product Perspective**

CMADS is a self-contained research prototype developed as part of a bachelor thesis. It does not integrate with any production clinical system, hospital information system, or real patient database. The system is composed of two loosely coupled subsystems that communicate through well-defined data artefacts:

-   The Data Pipeline Subsystem transforms raw synthetic data into structured Gold-layer case files (JSON).

-   The Multi-Agent Pipeline Subsystem consumes these case files and produces clinical decision reports through coordinated agent reasoning.

The system boundary is illustrated conceptually below. Synthetic data enters from the left (Synthea generation), flows through the data layers, and feeds into the agent orchestration pipeline, which produces the final clinical decision output.

**2.2 System Context and Boundaries**

The following elements are within the system boundary:

-   Synthetic patient data generation via Synthea (CSV and FHIR R4 JSON) --- the single source of all patient data.

-   Data ingestion, transformation, and enrichment across Bronze, Silver, Silver+, and Gold layers --- all derived from Synthea output.

-   Multi-agent orchestration, reasoning, and clinical decision generation.

-   Agent evaluation against ground truth labels.

The following elements are explicitly outside the system boundary:

-   Real patient data of any kind.

-   Integration with production EHR systems (e.g., Epic, Cerner).

-   Regulatory compliance (HIPAA, GDPR) --- not applicable as no real data is processed.

-   Clinician-facing user interfaces beyond basic output review.

-   Model training or fine-tuning --- the system uses a pre-trained LLM (GPT-o3 120B) served locally via Ollama.

**2.4 Assumptions**

-   Synthea's rule-based disease modules (state transition machines informed by CDC/NIH statistics) generate medically plausible synthetic records that are representative enough to exercise the agent pipeline meaningfully.

-   The locally hosted LLM (GPT-o3 120B served via Ollama) possesses sufficient medical knowledge to reason about clinical scenarios without domain-specific fine-tuning.

-   The OMOP CDM v5.4 mapping from Synthea outputs is sufficiently accurate for the purposes of this prototype; perfect clinical coding fidelity is not required.

-   The system will process one patient case at a time; batch processing and concurrency are not requirements for the thesis prototype.

-   Agent evaluation will be performed against ground truth labels derived from Synthea's structured data (conditions, medications, lab values), acknowledging that these labels are synthetic and not clinician-validated.

**2.5 Constraints**

-   **Thesis timeline:** The system must be developed, tested, and documented within the bachelor thesis timeframe.

-   **Compute budget:** Local GPU resources constrain the inference speed and batch size. Running GPT-o3 120B via Ollama requires sufficient VRAM; inference latency per agent will be higher than cloud API calls.

-   **No real clinical data:** The system shall never process, store, or transmit real patient information.

-   **Single-user operation:** The system is not required to support concurrent users or multi-tenancy.

-   **LLM availability:** The system depends on the local Ollama server being running. No external network connectivity is required for agent inference.

**2.6 Dependencies**

-   **Synthea:** The open-source synthetic patient generator (Java CLI) that serves as the single source of all patient data. Synthea uses a Generic Module Framework of state transition machines to simulate complete patient lifespans, outputting FHIR R4 JSON bundles and CSV files.

-   **Ollama:** Local LLM serving infrastructure. Ollama hosts GPT-o3 120B on the development machine at localhost:11434. LangChain's ChatOllama class provides native integration. No external API keys or network connectivity required for inference.

-   **OMOP Vocabulary Files:** SNOMED-CT, LOINC, and RxNorm concept tables for Silver-layer mapping.

-   **Multi-Agent Framework:** A framework supporting orchestrator-based agent coordination (e.g., LangGraph, CrewAI, or AutoGen).

**4. Interface Requirements**

This section specifies the interfaces through which CMADS components communicate with each other (internal) and with external systems or users (external). Because the multi-agent pipeline is the primary contribution, agent-to-agent and agent-to-orchestrator interfaces are specified in detail, while data pipeline interfaces are described at a summary level.

**4.1 Agent--Orchestrator Interface**

All communication between the Orchestrator and subordinate agents shall follow a uniform request--response contract. This interface is the backbone of the multi-agent pipeline.

  ------------ ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ ----------------
  **Req ID**   **Requirement**                                                                                                                                                                                                                                                                            **Priority**

  **IF-001**   Each agent invocation shall be triggered by the Orchestrator via a standardised Agent Request object containing: agent_id, patient_case_id, input_payload (JSON), execution_context (upstream outputs), and invocation_timestamp.                                                          Must

  **IF-002**   Each agent shall return a standardised Agent Response object containing: agent_id, patient_case_id, status (success \| partial \| error), output_payload (JSON conforming to the agent's output schema), confidence_score, token_usage (prompt + completion), and execution_duration_ms.   Must

  **IF-003**   The Agent Request and Agent Response schemas shall be versioned. Schema version shall be included in every request and response message.                                                                                                                                                   Should

  **IF-004**   When an agent returns status 'error' or 'partial', the response shall include an error_details field with a human-readable message and an error_code for programmatic handling.                                                                                                            Must

  **IF-005**   The Orchestrator shall pass upstream agent outputs to downstream agents exclusively through the execution_context field of the Agent Request, never through shared mutable state.                                                                                                          Must
  ------------ ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ ----------------

  **config_overrides**    object      No             Optional per-invocation overrides (e.g., temperature, max_tokens, model).

**5. Non-Functional Requirements**

This section specifies quality attributes and constraints that apply across the entire system. Requirements are grouped by category. Because CMADS is a thesis research prototype, non-functional requirements are calibrated accordingly --- the emphasis is on reproducibility, observability, and extensibility rather than production-grade scalability or availability.

**5.1 Reproducibility**

Reproducibility is the most critical non-functional quality for a thesis project. The system must allow any evaluator to re-run experiments and obtain comparable (though not necessarily identical, given LLM non-determinism) results.

  ------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------
  **Req ID**   **Requirement**                                                                                                                                                                                                            **Priority**

  **NF-001**   All agent prompts, system configurations, and pipeline parameters shall be stored in version-controlled configuration files (not hard-coded).                                                                              Must

  **NF-002**   Each pipeline execution shall record a complete run manifest: input patient_case_ids, agent configuration versions, LLM model identifiers, temperature settings, random seeds (where applicable), and framework version.   Must

  **NF-003**   The system shall support deterministic re-execution of the data pipeline given the same Synthea seed and configuration, producing identical Bronze-through-Gold outputs.                                                   Must

  **NF-004**   For the agent pipeline, the system shall log sufficient information (full prompts, model responses, parameters) to enable post-hoc analysis even when exact reproduction is not possible due to LLM non-determinism.       Must

  **NF-005**   The system shall support setting LLM temperature to 0 (or minimum available) for evaluation runs to minimise output variance.                                                                                              Should
  ------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------

**5.2 Observability and Logging**

Comprehensive logging is essential for debugging agent behaviour, understanding decision pathways, and writing the thesis analysis.

  ------------ --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------
  **Req ID**   **Requirement**                                                                                                                                                                         **Priority**

  **NF-010**   The system shall log every LLM call with: timestamp, agent_id, model, prompt (or hash), response (or summary), token counts, and latency.                                               Must

  **NF-011**   The Orchestrator shall produce a per-case execution timeline showing agent invocation order, dependencies, durations, and statuses in a structured format suitable for visualisation.   Must

  **NF-012**   Logs shall be structured (JSON lines format) and written to a configurable log directory, one file per pipeline run.                                                                    Must

  **NF-013**   The system shall track cumulative token usage and estimated cost per patient case and per evaluation run.                                                                               Must

  **NF-014**   Log verbosity shall be configurable (DEBUG, INFO, WARN, ERROR) without code changes, via environment variable or configuration file.                                                    Should
  ------------ --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------

**5.3 Performance**

Performance requirements are defined relative to the thesis context. The system processes one patient at a time; high throughput is not required, but reasonable execution time is necessary for iterative development and evaluation.

  ------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------
  **Req ID**   **Requirement**                                                                                                                                                            **Priority**

  **NF-020**   The complete agent pipeline (all agents, one patient case) shall complete within 15 minutes under normal local inference conditions with GPT-o3 120B via Ollama.           Should

  **NF-021**   The data pipeline (Bronze through Gold, full Synthea population) shall complete within 30 minutes for a population of up to 1,000 synthetic patients.                      Should

  **NF-022**   Individual agent invocations shall have a configurable timeout (default: 60 seconds). Exceeding the timeout shall be treated as a partial failure.                         Must

  **NF-023**   Where the execution graph permits (i.e., no data dependency between agents), the Orchestrator should support parallel agent invocation to reduce total pipeline latency.   Should
  ------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------

**5.4 Extensibility and Modularity**

The system architecture shall support experimentation with different agent configurations, additional agents, and alternative LLM backends --- a core requirement for thesis research.

  ------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------
  **Req ID**   **Requirement**                                                                                                                                                                                                            **Priority**

  **NF-030**   Adding a new agent to the pipeline shall require only: defining its prompt, input/output schema, and registering it in the Orchestrator's execution graph configuration. No changes to framework code shall be required.   Must

  **NF-031**   Removing or disabling an agent shall be achievable via configuration change, with the Orchestrator automatically adjusting the execution graph.                                                                            Should

  **NF-032**   The underlying LLM for any agent shall be swappable via configuration (model identifier in the agent's config), without modifying the agent's prompt or pipeline logic.                                                    Must

  **NF-033**   The Orchestrator's execution graph (agent ordering and dependencies) shall be defined declaratively in a configuration file (e.g., YAML or JSON), not hard-coded.                                                          Must

  **NF-034**   The system shall support multiple named pipeline configurations (e.g., 'full_pipeline', 'diagnostic_only', 'no_radiology') selectable at runtime.                                                                          Should
  ------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------

**5.5 Reliability and Error Handling**

  ------------ --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- ----------------

  **NF-040**   The failure of a single agent shall not cause the entire pipeline to abort. The Orchestrator shall continue with remaining agents and mark the failed agent's contribution as unavailable in downstream agents' input. *(Originally referenced Synthesis Agent; updated to reflect current architecture.)*   Must

  **NF-041**   LLM calls shall implement retry logic with configurable maximum retries (default: 3) and exponential backoff for Ollama server errors.                                                                                      Should

  **NF-042**   If an agent returns malformed output that fails schema validation, the Orchestrator shall log the raw output, mark the agent as 'partial', and continue the pipeline.                                                       Must

  **NF-043**   The system shall checkpoint pipeline state after each agent completes, enabling manual resume from the last successful agent in case of catastrophic failure.                                                               Should

**6.5 Glossary of Agent Roles**

A quick-reference summary of each agent's purpose in the pipeline.

  -------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------
  **Agent**                  **Role Summary**

  **Orchestrator**           Central coordinator. Controls sequencing, data routing, conflict detection, timeout enforcement, and execution logging across all agents.

  **EHR Analyst**            Primary intake. Consumes patient narratives and structured EHR data to produce a comprehensive clinical summary.

  **Lab Interpreter**        Laboratory specialist. Analyses lab results, trends, and critical flags to produce a prioritised findings list.

  **Diagnostic Reasoning**   Diagnostician. Synthesises clinical summary and lab findings to generate a ranked differential diagnosis with evidence mapping.

  **Treatment Planning**     Therapeutics advisor. Proposes medication and non-pharmacological treatment plans, checking for interactions and contraindications.

  **Clinical Reviewer**      Quality gate. Critically evaluates diagnostic and treatment outputs for consistency, completeness, and clinical soundness.

  **Radiology Agent**        *(Moved to separate data enrichment pipeline.)* Imaging specialist. Implemented as pipeline/radiology_agents.py, not as a MAS agent stage. Generates structured radiology reports in the Gold layer.

  **Diagnostic Refiner**     Final consolidator. Merges diagnostic reasoning and clinical reviewer outputs into a refined final differential diagnosis. Replaces the originally specified Synthesis Agent.

  **LLM Evaluator**          Automated evaluator. Compares the Diagnostic Refiner's final differential against Synthea ground truth to produce diagnostic accuracy metrics.

  **Synthesis Agent**        *(Replaced by Diagnostic Refiner.)* Originally specified as the final consolidator. Its role is now fulfilled by the Diagnostic Refiner Agent.
  -------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------

**6.6 Open Items and Future Work**

The following items are identified as outside the scope of this version of the SRD but are candidates for future iterations or thesis extensions.

-   RAG integration: Augmenting agent prompts with retrieval from clinical guidelines databases (e.g., UpToDate, PubMed) for evidence-based reasoning.

-   Human-in-the-loop: Adding a clinician review step between the Clinical Reviewer and Diagnostic Refiner agents, enabling interactive correction.

-   Multi-patient batch processing: Extending the Orchestrator to process patient cohorts in parallel for population-level analysis.

-   Agent self-reflection: Implementing a feedback loop where agents can revise their outputs based on downstream reviewer feedback before final synthesis.

-   Fine-tuned domain models: Evaluating the impact of using clinically fine-tuned LLMs versus general-purpose models on diagnostic accuracy.

-   Real clinical data pilot: Adapting the system for use with de-identified real clinical data under appropriate ethical approval.

-   Explainability dashboard: Building a visual interface that traces each element of the Clinical Decision Report back through the agent chain to its source data.
