## 2. Point-in-Time Approach

### 2.1 The Decision

All patient data shown to MAS agents is from **BEFORE the target disease was diagnosed**. The target disease is hidden from the condition list. This simulates a real clinical scenario: the doctor sees a patient with symptoms and lab results but hasn't made the diagnosis yet.

### 2.2 Implementation

- **Cutoff date** = `condition_start_date` of the target disease
- `ehr_case.json` contains only conditions, medications, visits, and imaging from before the cutoff
- The target disease SNOMED code is excluded from the condition list
- `ground_truth.json` stores the hidden answer (never shown to agents)
- Leakage verification confirms the target disease name does not appear in ehr_case

### 2.3 Why Not Show All Data?

If the MAS sees all current conditions including "Chronic congestive heart failure," it doesn't need to diagnose — the answer is already in the data. The point-in-time approach makes diagnosis a genuine reasoning task.

## 3. Disease Selection: What We Removed and Why

### 3.1 The Discovery Process

Through iterative testing, we discovered that many diseases in Synthea have **no lab evidence** before diagnosis. We systematically analysed each disease:

1. Checked if labs were ordered at disease-specific encounters
2. Checked if medications were prescribed for the disease
3. Compared lab values for patients WITH vs WITHOUT the disease
4. Checked hemoglobin values before/after anemia diagnosis (the definitive proof)

### 3.2 Diseases Removed

| Disease | Reason for Removal |
|---------|-------------------|
| **Anemia** | Hemoglobin normal before diagnosis. Synthea assigns incidentally (never encounter reason). Confirmed with Claude Opus cross-validation. |
| **Breast cancer** | Requires mammography/biopsy. No tumor markers in pre-diagnosis labs. |
| **Cerebral palsy** | Congenital. No lab markers exist. |
| **Epilepsy** | Requires EEG. No seizure-related labs in Synthea. |
| **Osteoporosis** | Requires DEXA scan. No bone density data. |
| **Pneumonia** | Requires chest imaging. No respiratory labs generated by Synthea's pneumonia module. |
| **Osteoarthritis** | Clinical/imaging diagnosis. Pain score is the only data point. |

### 3.3 Diseases Retained (8 Core)

| Disease | Why It Works |
|---------|-------------|
| **ESRD** | Creatinine, eGFR <15, electrolyte abnormalities — Synthea's renal module correlates |
| **CKD Stage 3** | eGFR <60, rising creatinine |
| **CKD Stage 2** | eGFR 60-89 |
| **CKD Stage 1** | Proteinuria, early creatinine changes |
| **CHF** | LVEF, BNP, cardiac medications (furosemide, carvedilol) |
| **IHD** | Cardiac history, troponin, coronary medications |
| **Diabetes T2** | HbA1c, glucose, metformin/insulin |
| **Hypertension** | BP readings, antihypertensive medications |
| **Metabolic Syndrome** | Triglycerides, HDL, glucose, BP — multiple measurable criteria |

## 4. The Three Filtering Layers

### 4.1 Layer 1: Disease Selection Filter

**Where:** `pipeline/gold.py` → `TARGET_DISEASES` list

**What it does:** Only diseases with demonstrated lab evidence are included as target diseases.

**Implementation:** A Python list of disease names. The `select_target_encounter()` function only selects targets from this list.

### 4.2 Layer 2: Data Sufficiency Filter

**Where:** `pipeline/gold.py` → `MIN_PRE_DIAGNOSIS_VISITS` and `MIN_PRE_DIAGNOSIS_LABS`

**What it does:** Each patient must have:
- ≥3 encounters before the diagnosis date
- ≥5 lab observations before the diagnosis date

**Why these thresholds:**
- 3 visits ensures the patient has some clinical history
- 5 labs ensures the MAS has at least basic bloodwork to interpret
- Lower thresholds let through patients with empty data
- Higher thresholds exclude too many patients

**Implementation:** SQL subqueries in `select_target_encounter()` count visits and labs before the candidate diagnosis date.

### 4.3 Layer 3: LLM Lab Verifier

**Where:** `pipeline/lab_verifier_llm.py`

**What it does:** For each patient, asks Qwen3 32B: "Could a doctor detect this disease from these labs?" Only patients with confidence ≥80 pass.

**Why an LLM instead of rules:**
- We first built a hardcoded rule-based verifier (`pipeline/lab_verifier.py`) with criteria like `creatinine > 4.0 → ESRD`
- Rules found 22 patients passing out of 100
- The LLM found 34 patients — 55% more — because it catches **combinations** that rules miss (e.g., creatinine 3.8 + eGFR 14 + proteinuria = ESRD even though creatinine alone is below 4.0)

**Confidence threshold evolution:**
- Initially no threshold → too many false positives
- Threshold 70 → let through borderline cases (DM2 with HbA1c 6.4%) that the MAS couldn't diagnose
- Threshold 80 → filters borderline cases, only clear evidence passes

## 5. Gold Layer Assembly

### 5.1 Target Disease Selection

For each patient, the Gold layer selects the most clinically significant target disease:

**Priority ranking:**
1. Heart failure, neoplasms, IHD, ESRD (priority 1)
2. Diabetes, CKD stage 3, aortic valve (priority 2)
3. Epilepsy, other CKD, metabolic syndrome (priority 3)
4. Others (priority 4)

Within the same priority, the **most recent** diagnosis is selected (maximises pre-diagnosis history).

### 5.2 Case File Assembly

Three files per patient:

**ehr_case.json:**
- Demographics (age at cutoff, gender, race, location)
- Active conditions before cutoff (target excluded)
- Resolved conditions
- Medications active at cutoff (with drug-condition links)
- Visit summary (counts by class)
- Risk scores (BP category, glycemic control, Charlson index)
- Comorbidity flags (has_ihd, has_hypertension, etc.)
- Imaging studies before cutoff

**lab_case.json:**
- Latest lab values before cutoff
- Lab trends (increasing/decreasing/stable)
- Critical lab flags (severity levels)
- Recent vitals (BP, HR, BMI, etc.)

**ground_truth.json:**
- Target disease name and SNOMED code
- Diagnosis date
- Cutoff date
- All conditions at time of diagnosis
- Post-diagnosis medications
- Labs at cutoff

### 5.3 Leakage Prevention

The target disease is excluded by SNOMED code:
```sql
WHERE condition_source_code != ? -- target disease code
```

Verified: Leakage check confirms the target disease name does not appear in any ehr_case.json.

## 6. Condition Names: The `condition` vs `name` Bug

### Discovery

During testing, some patients showed conditions as `? (SNOMED: 431855005)` instead of `Chronic kidney disease stage 1`. The EHR Analyst couldn't interpret raw SNOMED codes.

### Cause

The Gold layer stored condition names using the key `condition`, but the EHR Analyst's prompt builder looked for the key `name`. When it didn't find `name`, it showed `?`.

### Fix

Updated the EHR Analyst's `build_user_prompt()` to check both keys:
```python
name = c.get('condition', c.get('name', 'Unknown'))
```

## 8. Radiology Report Generation (Separate Pipeline)

Radiology reports are generated separately and stored in `data/gold/radiology_reports/`. They are **not part of the current MAS pipeline** but are available for future integration.

Key details:
- 4-agent pipeline: Data Collector → Generator → Evaluator → Storage
- Generator: GPT-oss 120B on Groq
- Evaluator: Qwen3 32B on Groq
- 6-tier imaging selection for each patient
- Retry-with-feedback loop (max 3 retries)
- 503 patients with imaging, 497 without
